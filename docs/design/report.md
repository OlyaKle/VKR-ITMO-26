## 1. Предметная область и требования

### Описание предметной области

Система предназначена для анализа эффективности работы отдела. Она получает данные о рабочих задачах, сроках их выполнения и загрузке сотрудников, рассчитывает основные показатели и показывает результаты в удобном виде.

Сотрудники и руководитель отдела смогут просматривать показатели работы, а руководитель дополнительно — получать с помощью ИИ объяснение выявленных проблем и рекомендации по улучшению рабочих процессов.

Система должна сократить время на сбор и обработку данных, упростить контроль выполнения задач и помочь находить проблемы в работе отдела.

### Функциональные требования

Функциональные требования описывают, **что система должна уметь делать**.

| ID | Требование | Как проверить выполнение |
|---|---|---|
| FR-01 | Система должна получать данные о задачах из внешнего источника, например Jira. | Подключить источник и проверить, что задачи загружены в систему. |
| FR-02 | Система должна сохранять полученные данные о задачах, сроках, статусах и исполнителях. | Проверить наличие загруженных данных в системе. |
| FR-03 | Система должна автоматически рассчитывать показатели работы отдела: количество выполненных и незавершённых задач, долю просроченных задач, среднее время выполнения и загрузку сотрудников. | Сравнить рассчитанные показатели с результатами ручного расчёта. |
| FR-04 | Система должна показывать рассчитанные показатели в виде таблиц и графиков. | Проверить отображение показателей на экране. |
| FR-05 | Система должна позволять выбирать период, за который отображаются показатели. | Выбрать разные периоды и проверить изменение результатов. |
| FR-06 | Система должна сравнивать показатели за разные периоды и показывать их изменения. | Сравнить результаты за два выбранных периода. |
| FR-07 | Система должна передавать рассчитанные показатели ИИ для анализа. | Проверить, что ИИ получает необходимые данные. |
| FR-08 | Система должна выявлять с помощью ИИ возможные проблемы в работе отдела и объяснять причины их появления на основе доступных данных. | Передать данные с заранее заданной проблемой и проверить результат анализа. |
| FR-09 | Система должна формировать рекомендации по улучшению работы отдела на основе результатов анализа. | Проверить, что по результатам анализа сформированы рекомендации. |
| FR-10 | Система должна сохранять результаты анализа и рекомендации, чтобы их можно было просмотреть позднее. | Выполнить анализ и проверить наличие сохранённого результата. |

### Нефункциональные требования

Нефункциональные требования описывают, **какими свойствами должна обладать система и какие ограничения она должна соблюдать**.

| ID | Требование | Как проверить выполнение |
|---|---|---|
| NFR-01 | Основные страницы с показателями должны загружаться не более чем за 5 секунд при обычном объёме данных. | Измерить время загрузки страниц. |
| NFR-02 | Доступ к данным и функциям системы должен предоставляться только авторизованным пользователям. | Проверить, что без входа в систему нельзя открыть закрытые разделы. |
| NFR-03 | Система должна сохранять данные и результаты анализа после завершения работы и повторного запуска. | Перезапустить систему и проверить сохранность данных. |
| NFR-04 | Система должна сообщать об ошибках получения данных и проблемах при выполнении анализа. | Смоделировать ошибку и проверить появление сообщения. |
| NFR-05 | Интерфейс системы должен быть понятным и позволять просматривать основные показатели без специальных технических знаний. | Проверить выполнение основных действий через интерфейс. |

*Примечание: числовые ограничения, например 5 секунд, — предлагаемые целевые значения. Их можно изменить после определения технических возможностей проекта.*

## 3. Выбор нотаций для проекта

Для проектирования системы предлагается использовать четыре нотации: BPMN, UML Use Case, ER-диаграмму и C4-модель.

| Нотация или вид диаграммы | Что моделируем | Связанные требования | Почему подходит |
|---|---|---|---|
| BPMN | Процесс сбора данных, расчёта показателей и получения рекомендаций. | FR-01–FR-09 | Показывает последовательность действий и позволяет сравнить текущий процесс с предлагаемым. |
| UML Use Case | Возможности системы для сотрудника и руководителя. | FR-03–FR-10, NFR-02 | Показывает, кто и какие функции может использовать. |
| ER-диаграмма | Структуру базы данных: пользователи, задачи, показатели, результаты анализа и рекомендации. | FR-02, FR-03, FR-06, FR-10, NFR-03 | Помогает определить, какие данные нужно хранить и как они связаны между собой. |
| C4-модель | Основные части системы и связи между ними. | FR-01, FR-07–FR-10, NFR-01–NFR-04 | Показывает взаимодействие интерфейса, базы данных, источника задач и ИИ. |

**Почему выбраны именно эти нотации:**

- BPMN нужна для описания рабочих процессов и сравнения их до и после внедрения системы.
- UML Use Case показывает функции системы и доступные пользователям действия.
- ER-диаграмма помогает спроектировать хранение рабочих данных и результатов анализа.
- C4-модель показывает, из каких частей состоит система и как они взаимодействуют.

## 4. Модели системы

Для выполнения требований лабораторной работы предлагается подготовить четыре модели.

### 4.1. Диаграмма вариантов использования (UML Use Case)

**Диаграмма:** вставить UML Use Case.

**Пояснение модели:**

Диаграмма показывает, какие действия могут выполнять пользователи системы.

Предусматриваются две роли:

- **Сотрудник:** просмотр показателей работы отдела.
- **Руководитель:** просмотр показателей, выбор периода анализа, запуск ИИ-анализа, просмотр проблем и рекомендаций.

**Отражённые функциональные требования и элементы модели:**

- FR-03 — просмотр рассчитанных показателей.
- FR-04 — просмотр таблиц и графиков.
- FR-05 — выбор периода.
- FR-07 — запуск ИИ-анализа.
- FR-08 — просмотр выявленных проблем.
- FR-09 — просмотр рекомендаций.
- FR-10 — просмотр сохранённых результатов.

**Нефункциональные требования и проектные решения:**

NFR-02 учитывается разделением прав пользователей: сотрудник и руководитель имеют доступ к разным возможностям системы.

### 4.2. ER-диаграмма базы данных

**Диаграмма:** вставить ER-диаграмму.

**Пояснение модели:**

Диаграмма показывает, какие данные хранит система и как они связаны между собой.

Предлагается выделить следующие основные сущности:

- **Пользователь** — данные о пользователе и его роли.
- **Сотрудник** — информация о сотруднике отдела.
- **Задача** — название, статус, исполнитель, даты создания и завершения, срок выполнения.
- **Показатель** — название показателя, его значение и период расчёта.
- **Анализ** — дата проведения и результаты ИИ-анализа.
- **Рекомендация** — текст рекомендации, связанный с результатом анализа.

**Отражённые функциональные требования и элементы модели:**

- FR-02 — хранение данных о задачах.
- FR-03 — хранение рассчитанных показателей.
- FR-06 — хранение показателей за разные периоды.
- FR-10 — хранение результатов анализа и рекомендаций.

**Нефункциональные требования и проектные решения:**

NFR-03 учитывается за счёт хранения данных в базе данных, что позволяет сохранять их после перезапуска системы.

### 4.3. C4-модель

**Диаграмма:** вставить C4-модель с основными компонентами системы.

**Пояснение модели:**

C4-модель показывает, из каких основных частей состоит система и как они взаимодействуют.

В системе предусматриваются следующие компоненты:

- **Пользовательский интерфейс** — отображает показатели, графики и рекомендации.
- **Модуль получения данных** — загружает информацию о задачах из Jira.
- **Модуль расчёта показателей** — обрабатывает данные и рассчитывает метрики.
- **База данных** — хранит задачи, показатели и результаты анализа.
- **Модуль ИИ-анализа** — передаёт данные языковой модели, получает объяснения и рекомендации.

**Отражённые функциональные требования и элементы модели:**

- FR-01 — получение данных из Jira.
- FR-02 — сохранение полученных данных.
- FR-03 — расчёт показателей.
- FR-07 — передача показателей на ИИ-анализ.
- FR-08 — выявление проблем.
- FR-09 — формирование рекомендаций.
- FR-10 — сохранение результатов анализа.

**Нефункциональные требования и проектные решения:**

- NFR-01 — разделение системы на отдельные компоненты упрощает обработку запросов.
- NFR-03 — база данных обеспечивает сохранение информации.
- NFR-04 — обработка ошибок должна предусматриваться при получении данных и обращении к ИИ.

### 4.4. BPMN-диаграмма процесса анализа эффективности

**Диаграмма:** вставить BPMN-диаграмму процесса работы системы.

**Пояснение модели:**

Диаграмма показывает последовательность действий от получения рабочих данных до формирования рекомендаций.

Основные этапы:

1. Получение данных о задачах.
2. Сохранение полученной информации.
3. Расчёт показателей работы отдела.
4. Отображение показателей пользователю.
5. Передача показателей на ИИ-анализ.
6. Выявление проблем и подготовка рекомендаций.
7. Сохранение результатов анализа.

**Отражённые функциональные требования и элементы модели:**

FR-01–FR-10 — диаграмма показывает общий процесс получения данных, их обработки, анализа и отображения результатов.

**Нефункциональные требования и проектные решения:**

NFR-04 учитывается добавлением обработки ошибок при получении данных и выполнении ИИ-анализа.

## 5. AS-IS и TO-BE

**Выбранная нотация:** BPMN.

### AS-IS — текущее состояние

**Диаграмма:** вставить BPMN-диаграмму текущего процесса без предлагаемой системы.

**Описание и ограничения:**

В текущем процессе руководитель отдела самостоятельно собирает данные о задачах из рабочих инструментов, проверяет сроки, рассчитывает показатели и сравнивает результаты.

При необходимости выявления проблем приходится вручную анализировать полученную информацию и самостоятельно придумывать способы улучшения работы.

Основные ограничения:

- данные находятся в разных источниках;
- показатели приходится рассчитывать вручную;
- сложно быстро сравнивать результаты за разные периоды;
- выявление проблем и подготовка рекомендаций требуют дополнительного времени.

### TO-BE — предлагаемое состояние

**Диаграмма:** вставить BPMN-диаграмму процесса с использованием разрабатываемой системы.

**Описание изменений:**

После внедрения системы процесс анализа становится автоматизированным.

Система получает данные о задачах, сохраняет их, рассчитывает показатели и отображает результаты в виде таблиц и графиков. Затем ИИ анализирует показатели, помогает выявить проблемы и формирует рекомендации.

Руководитель получает готовые результаты анализа и может использовать их для принятия решений.

### Обоснование перехода

Переход от AS-IS к TO-BE обеспечивается следующими изменениями:

| Было (AS-IS) | Станет (TO-BE) |
|---|---|
| Ручной сбор данных | Автоматическое получение данных из Jira |
| Ручной расчёт показателей | Автоматический расчёт метрик |
| Самостоятельное сравнение показателей | Просмотр изменений за выбранные периоды |
| Ручной поиск проблем | Выявление возможных проблем с помощью ИИ |
| Самостоятельная подготовка рекомендаций | Автоматическое формирование рекомендаций |

В результате сокращается количество ручных действий, ускоряется анализ работы отдела и появляется возможность быстрее находить проблемные участки.
